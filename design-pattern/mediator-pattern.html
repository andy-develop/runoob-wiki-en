中介者模式

The Mediator Pattern is used to reduce the communication complexity between multiple objects and classes, and it is a behavioral pattern.

The Mediator Pattern defines a mediator object to encapsulate the interactions between a series of objects. The mediator enables objects to avoid explicit mutual references, thereby loosening their coupling and allowing the interactions between them to be changed independently.

介绍

意图

By introducing a mediator object to encapsulate and coordinate the interactions between multiple objects, the coupling between objects is reduced.

Main problems solved

  • It solves complex one-to-many association problems between objects, avoids high coupling between objects, and simplifies the system structure.

使用场景

  • When multiple classes in the system are coupled with each other, forming a network structure.

实现方式

  • Define the mediator interface: Specifies the interface that the mediator must implement.
  • Create the concrete mediator: Implements the mediator interface, containing the logic for coordinating the interactions between colleague objects.
  • 定义同事类: Each object no longer needs to explicitly reference one another, but interacts through the mediator.

关键代码

  • 中介者: Encapsulates the interaction logic between objects.
  • 同事类: Communicate through the mediator.

应用实例

  1. WTO: After China joined the WTO, countries trade through the WTO, which simplifies bilateral relations.
  2. Airport dispatch system: Coordinates aircraft takeoffs and landings, runway usage, etc.
  3. MVC框架: The controller acts as the mediator between the model and the view.

优点

  1. 降低复杂度: Converts the one-to-many relationship between multiple objects into a one-to-one relationship.
  2. 解耦: Objects no longer directly reference one another; they interact through the mediator.
  3. Conforms to the Law of Demeter: Objects only need to know the mediator, not other objects.

缺点

  • Mediator complexity: The mediator may become huge and complex, making it difficult to maintain.

使用建议

  • When there are complex reference relationships between objects in the system, consider using the Mediator Pattern.
  • Encapsulate the behavior of multiple classes through the mediator to avoid generating too many subclasses.

注意事项

  • Avoid using the Mediator Pattern when responsibilities are unclear or chaotic, as this may cause the mediator to assume too many responsibilities.

结构

The Mediator Pattern includes the following main roles:

  • Mediator: Defines an interface for communicating with each colleague object and manages the relationships between colleague objects. It usually includes one or more event handling methods for processing various interaction events.

  • Concrete Mediator: Implements the mediator interface and is responsible for implementing the communication logic between colleague objects. It maintains references to each colleague object and coordinates their interactions.

  • Colleague objects (Colleague): Defines an interface for communicating with the mediator. It usually includes a method for sending messages and a method for receiving messages.

  • Concrete Colleague: Implements the colleague object interface and is the object that truly participates in the interaction. It sends its messages to the mediator, which forwards them to other colleague objects.

    What is the Mediator pattern?

    In real life, there are many instances of the Mediator pattern, such as the QQ game platform, chat rooms, QQ groups, SMS platforms, and real estate agencies. Whether it is QQ games or QQ groups, they all serve as an intermediate platform. QQ users can log in to this intermediate platform to communicate with other QQ users. Without these intermediate platforms, if we wanted to chat with friends, we might have to do so in person. Phone calls and text messages are also intermediate platforms. With this intermediate platform, each user does not need to directly depend on other users; they only need to depend on the intermediate platform, and all operations are distributed by the intermediate platform.

    The Mediator Pattern defines a mediator object to encapsulate the interaction relationships between a series of objects. The mediator enables objects to avoid explicit mutual references, thereby reducing coupling and allowing their interaction behavior to be changed independently.

    Design approach and code implementation:

    Use a real-life card game example to implement the Mediator Pattern. In a card game, there are always winners and losers, which correspond to changes in money. If the Mediator Pattern is not used, the implementation is as follows:

    /// <summary>
/// 抽象牌友类
/// </summary>
public abstract class AbstractCardPartner
{
    public int Money { get; set; }
 
    public abstract void ChangeMoney(int money, AbstractCardPartner other);
}
 
/// <summary>
/// 牌友A
/// </summary>
public class PartnerA : AbstractCardPartner
{
    public override void ChangeMoney(int money, AbstractCardPartner other)
    {
        Money += money;
        other.Money -= money;
    }
}
 
/// <summary>
/// 牌友B
/// </summary>
public class PartnerB : AbstractCardPartner
{
    public override void ChangeMoney(int money, AbstractCardPartner other)
    {
        Money += money;
        other.Money -= money;
    }
}
 
/// <summary>
/// 调用
/// </summary>
/// <param name="args"></param>
static void Main(string[] args)
{
    AbstractCardPartner A = new PartnerA();
    A.Money = 20;
    AbstractCardPartner B = new PartnerB();
    B.Money = 20;
 
    // A赢了B的钱减少
    A.ChangeMoney(5, B);
    Console.WriteLine("A 现在的钱是：{0}", A.Money); // 应该是25
    Console.WriteLine("B 现在的钱是：{0}", B.Money); // 应该是15
 
    // B赢了A的钱减少
    B.ChangeMoney(10, A);
    Console.WriteLine("A 现在的钱是：{0}", A.Money); // 应该是15
    Console.WriteLine("B 现在的钱是：{0}", B.Money); // 应该是25
 
    Console.ReadLine();
}

    Such an implementation does solve the problem in the above scenario, and uses an abstract class so that both specific player A and player B depend on the abstract class, thereby reducing coupling between colleague classes. However, if player A changes, it will affect the state of player B. If more objects are involved, a change in one player will affect the state of all other associated players. For example, if player A miscalculates the money, then both player A and player B's money amounts will be incorrect. If multiple people are playing cards, the number of affected objects will be even greater. At this point, we might think - can we leave the task of calculating money to a program or someone good at arithmetic? This is how card games like Happy Landlord in QQ Games came to be.

    A further improved solution is to add a mediator object to coordinate the associations between objects. This is the application of the Mediator Pattern. The improved implementation code is shown below:

    /// <summary>
/// 抽象牌友类
/// </summary>
public abstract class AbstractCardPartner
{
    public int Money { get; set; }
 
    public abstract void ChangeMoney(int money, AbstractMediator mediator);
}
 
/// <summary>
/// 牌友A
/// </summary>
public class PartnerA : AbstractCardPartner
{
    public override void ChangeMoney(int money, AbstractMediator mediator)
    {
        mediator.AWin(money);
    }
}
 
/// <summary>
/// 牌友B
/// </summary>
public class PartnerB : AbstractCardPartner
{
    public override void ChangeMoney(int money, AbstractMediator mediator)
    {
        mediator.BWin(money);
    }
}
 
/// <summary>
/// 抽象中介者类
/// </summary>
public abstract class AbstractMediator
{
    protected AbstractCardPartner A;
    protected AbstractCardPartner B;
 
    public AbstractMediator(AbstractCardPartner a, AbstractCardPartner b)
    {
        A = a;
        B = b;
    }
 
    public abstract void AWin(int money);
    public abstract void BWin(int money);
}
 
/// <summary>
/// 调用
/// </summary>
/// <param name="args"></param>
static void Main(string[] args)
{
    AbstractCardPartner A = new PartnerA();
    AbstractCardPartner B = new PartnerB();
    A.Money = 20;
    B.Money = 20;
 
    AbstractMediator mediator = new MediatorPater(A, B);
 
    // A赢了
    A.ChangeMoney(5, mediator);
    Console.WriteLine("A 现在的钱是：{0}", A.Money); // 应该是25
    Console.WriteLine("B 现在的钱是：{0}", B.Money); // 应该是15
 
    // B赢了
    B.ChangeMoney(10, mediator);
    Console.WriteLine("A 现在的钱是：{0}", A.Money); // 应该是15
    Console.WriteLine("B 现在的钱是：{0}", B.Money); // 应该是25
 
    Console.ReadLine();
}

    In the implementation code above, the abstract mediator class stores two abstract card player classes. If a new card player class is added, the abstract mediator class has to be modified. This can be solved by combining the Observer Pattern, that is, the abstract mediator object stores the categories of the abstract card players, then adds Register and UnRegister methods to manage the list. Then, in the concrete mediator class, modify the AWin and BWin methods to traverse the list and change the money amounts of itself and other card players. This design still has a problem: when a new card player is added, although it solves the issue of not needing to modify the abstract mediator class, the concrete mediator class still has to be modified, that is, a CWin method needs to be added. The State Pattern can be used to solve this problem, and the State Pattern will be introduced in the next article.

    Advantages and disadvantages of the Mediator pattern

    优点：

    • It simplifies the relationships between objects, encapsulates the mutual relationships between objects in the system, and decouples each colleague class, making the system loosely coupled.
    • It provides system flexibility, making each colleague object independent and easy to reuse.

    缺点：

    • In the Mediator Pattern, the mediator role assumes a great deal of responsibility, so once the mediator object has a problem, the entire system will be greatly affected.
    • When adding a new colleague class, the abstract mediator class and the concrete mediator class have to be modified. At this point, the Observer Pattern and the State Pattern can be used to solve this problem.

    Applicable scenarios for the Mediator pattern

    The Mediator Pattern can be considered in the following situations:

    • A group of well-defined objects need to communicate with each other in a complex way.
    • You want to encapsulate the behavior of multiple classes through an intermediate class without generating too many subclasses.
