桥接模式

Bridge is used to decouple abstraction from implementation so that the two can vary independently. This type of design pattern is a structural pattern, which decouples the two by providing a bridge structure between abstraction and implementation.

This pattern involves an interface that acts as a bridge, so that the functionality of entity classes is independent of the interface implementation classes. These two types of classes can be structurally changed without affecting each other.

The purpose of the Bridge pattern is to separate abstraction from implementation so that they can vary independently. The pattern separates the abstract part of an object from its implementation part, allowing them to change independently. It connects the abstract and implementation parts through composition rather than inheritance.

We use the following example to demonstrate the usage of the Bridge Pattern. Here, we can use the same abstract class methods but different bridge implementation classes to draw circles of different colors.

介绍

意图

Used to separate the abstract part from the implementation part so that they can vary independently.

Main problems solved

Avoids the class explosion problem caused by inheritance and provides a more flexible way to extend.

使用场景

The Bridge pattern is suitable when a system may be classified from multiple perspectives and each perspective may vary independently.

实现方式

  • Separating multi-angle classification: Separates classification logic from different perspectives, allowing them to vary independently.
  • 减少耦合: Reduces coupling between abstraction and implementation.

关键代码

  • 抽象类: Defines an abstract class as part of the system.
  • 实现类: Defines one or more implementation classes that are associated with the abstract class through aggregation (rather than inheritance).

应用实例

  • 转世投胎: The separation of soul (abstraction) and body (implementation), allowing the soul to choose different bodies.
  • 墙上的开关: The separation of switch (abstraction) and internal implementation (implementation); users do not need to care about the internal working mechanism of the switch.

优点

  • Separating abstraction from implementation: Improves the flexibility and maintainability of the system.
  • 扩展能力强: Abstraction and implementation can be extended independently.
  • Transparent implementation details: Users do not need to understand implementation details.

缺点

  • Difficulty of understanding and design: The Bridge pattern increases the difficulty of understanding and designing the system.
  • 聚合关联: Requires developers to design and program at the abstraction level.

使用建议

  • Use the Bridge pattern when the system needs to increase flexibility between the abstraction role and the concrete role.
  • The Bridge pattern is especially suitable for systems where inheritance is undesirable or where multi-level inheritance causes a sharp increase in the number of classes.
  • Use the Bridge pattern when a class has two independently varying dimensions and both dimensions need to be extended.

注意事项

  • The Bridge pattern is suitable for two independently varying dimensions, ensuring that they can be extended and changed independently.

结构

The following are several key roles of the Bridge pattern:

  • Abstraction: Defines the abstract interface, usually containing a reference to the implementation interface.
  • Refined Abstraction: An extension of the abstraction, which can be a subclass of the abstract class or a concrete implementation class.
  • Implementor: Defines the implementation interface and provides the interface for basic operations.
  • Concrete Implementor: A concrete class that implements the implementation interface.

    Bridge Pattern: Bridge Pattern

    Place abstraction and implementation in two different class hierarchies so that they can vary independently. — "Head First Design Patterns"

    将类的功能层次结构和实现层次结构相分离，使二者能够独立地变化，并在两者之间搭建桥梁，实现桥接. — "Illustrated Design Patterns"

    Functional hierarchy of classes: The parent class has basic functions, and new functions are added in subclasses.

    Implementation hierarchy of classes: The parent class defines the interface by declaring abstract methods, and subclasses implement the interface by implementing concrete methods.

    There are four roles in the Bridge Pattern:

    抽象化角色: Uses the interface provided by the implementor role to define the basic function interface.

    Holds the implementor role and delegates to it in the functional interface, playing the role of building a bridge.

    Note that the abstraction role does not mean it is an abstract class, but rather that it abstracts the implementation.

    改善后的抽象化角色: As a subclass of the abstraction role, it adds new functions, that is, adds new interfaces (methods); it forms a functional class hierarchy with it.

    实现者角色: Provides the interface used by the abstraction role; it is an abstract class or interface.

    具体的实现者角色: As a subclass of the implementor role, it implements the interface by implementing concrete methods; it forms an implementation class hierarchy with it.

    If abstraction and implementation cannot vary independently, it is not the Bridge pattern.

    In the Bridge pattern, the concrete implementation classes are implemented in the interface that acts as a "bridge", and the "bridge" interface contains only abstract methods that implement functionality; concrete implementation classes inherit the "bridge" rather than directly inheriting the abstract class of the implementation class. The abstract class and the concrete implementation classes are structurally independent of each other, and changes in either do not affect the other. As long as the "bridge" remains unchanged, changes in the two will not affect each other.

    For the example program in the above tutorial, the concrete implementations are RedCircle and GreenCircle, and their abstract class is Shape. According to general logic, we directly inherit Shape to create different concrete objects. However, in the Bridge Pattern, the connection between abstraction and concrete implementation is established through the "bridge" DrawAPI, and the methods in DrawAPI are called to achieve the concrete implementation.

    Python 方式：

    # Bridge Pattern with Python Code
from abc import  abstractmethod,ABCMeta

# 创建桥接实现接口
class DrawAPI(metaclass=ABCMeta):
    @abstractmethod
    def drawCircle(self,inRadius,inX,inY):
        pass
# 创建实现了DrawAPI接口的实体桥接实现类
class RedCircle(DrawAPI):
    def drawCircle(self,inRadius,inX,inY):
        print("Drawing Circle [ color: red , radius: {0} , x : {1} , y : {2}]".format(inRadius, inX, inY))
class GreenCircle(DrawAPI):
    def drawCircle(self,inRadius,inX,inY):
        print("Drawing Circle [ color: green , radius: {0} , x : {1} , y : {2}]".format(inRadius, inX, inY))

# 使用DrawAPI接口创建抽象类Shape
class Shape(metaclass=ABCMeta):
    _drawAPI = None
    def __init__(self, inDrawAPI):
        self._drawAPI = inDrawAPI
# 创建实现了Shape接口的实体类
class Circle(Shape):
    _intX = 0
    _intY = 0
    _intRadius = 0
    def __init__(self,inX,inY,inRadius,inDrawAPI):
        Shape.__init__(self,inDrawAPI)
        self._intX = inX
        self._intY = inY
        self._intRadius = inRadius
    def draw(self):
        self._drawAPI.drawCircle(self._intRadius,self._intX,self._intY)

# 调用输出
if __name__ == '__main__':
    redCircle = Circle(100,100,10, RedCircle())
    greenCircle = Circle(100,100,10, GreenCircle())

    redCircle.draw()
    greenCircle.draw()

    PHP 实现：

    /**
 * Interface DrawAPI
 * 实现化(Implementor)角色：这个角色给出实现化角色的接口，但不给出具体的实现。
 */
interface DrawAPI
{
    public function drawCircle(int $radius, int $x, int $y);
}

/**
 * Class RedCircle
 * 具体实现化(ConcreteImplementorA)角色
 * 这个角色给出实现化角色接口的具体实现。
 */
class RedCircle implements DrawAPI
{

    public function drawCircle(int $radius, int $x, int $y)
    {
        echo "Drawing Circle[ color: red, radius: " . $radius . ", x: " . $x . ", " . $y . "]" . PHP_EOL;
    }
}

class GreenCircle implements DrawAPI
{

    public function drawCircle(int $radius, int $x, int $y)
    {
        echo "Drawing Circle[ color: green, radius: " . $radius . ", x: " . $x . ", " . $y . "]" . PHP_EOL;
    }
}

/**
 * Class Shape
 * 抽象化(Abstraction)角色
 * 给出定义,并保存一个对象实例化的引用
 */
abstract class Shape{
    protected $_drawAPI;
    public function __construct(DrawAPI $drawAPI)
    {
        $this->_drawAPI = $drawAPI;
    }
    public abstract function draw();
}

/**
 * Class Circle
 * 修正抽象化角色 RefinedAbstraction
 * 扩展抽象化角色，改变和修正父类对抽象化的定义。
 */
class Circle extends Shape{
    private $_x;
    private $_y;
    private $_radius;

    public function __construct(int $x,int $y,int $radius,DrawAPI $drawAPI)
    {
        parent::__construct($drawAPI);
        $this->_x = $x;
        $this->_y = $y;
        $this->_radius = $radius;
    }

    public function draw()
    {
        // TODO: Implement draw() method.
        $this->_drawAPI->drawCircle($this->_x,$this->_y,$this->_radius);
    }
}

class Demo{
    public static function main(){
        $red = new Circle(100,100,10,new RedCircle());
        $green = new Circle(100,100,10,new GreenCircle());
        $red->draw();
        $green->draw();
    }
}

Demo::main();

    In plain terms, if you have 3 brushes with different nibs and 12 colors of paint, you can draw 3 * 12 kinds of lines; but crayons would need 36 crayons to achieve the same effect.

    The former brush is the Bridge pattern (different brush models are one varying dimension, different paint colors are another varying dimension, and the two dimensions do not affect each other), while the latter crayon is multiple inheritance (brush model and paint color affect the crayon together). After understanding this, let us abstract it into code descriptions:

    The pen class is an abstract class with a method draw(). If we want to use a brush, we need to put in a color, then execute the draw method to draw that color.

    public abstract class Pen {
    public abstract void draw(Color color);
}

    We can inherit the pen abstract class to implement multiple brush models.

    public class PenOne extends Pen {
    public void draw(Color color) {
        System.out.println("当前一号笔在使用" + color.use() + "画画");    
    }
}
public class PenTwo extends Pen {
    public void draw(Color color) {
        System.out.println("当前二号笔在使用" + color.use() + "画画");    
    }
}

    color is an interface, and its implementation classes include red, blue, and so on.

    public interface Color {

    public String use();
}
public class Blue implements Color {
    public String use() {
        return "蓝色";    
    }
}
public class Red implements Color {
    public String use() {
        return "红色";    
    }
}

    Then we can start drawing:

    public class User {
    public static void main(String[] args) {
        Pen pen = new PenOne();        
        pen.draw(new Red());    
    }
}

    Output: The current pen No. 1 is drawing in red.

    At this point, to extend a brush model, we only need to add a new implementation class of Pen, and the paint box classes are not affected; similarly, when extending the number of paints, the brushes are not affected.

    The core idea of the Bridge pattern is to separate abstraction from implementation so that they can vary independently without affecting each other. The abstract part is responsible for defining the abstract interface, and the implementation part is responsible for providing concrete implementations. Through the Bridge pattern, the abstract part and the implementation part can be extended and changed independently without affecting each other.

    The following is a simple example showing how to use the Bridge pattern to connect the abstract part and the implementation part:

    // 实现接口
interface Implementor {
    void operationImpl();
}

// 具体实现类
class ConcreteImplementorA implements Implementor {
    @Override
    public void operationImpl() {
        // 具体实现A
    }
}

class ConcreteImplementorB implements Implementor {
    @Override
    public void operationImpl() {
        // 具体实现B
    }
}

// 抽象类
abstract class Abstraction {
    protected Implementor implementor;

    public Abstraction(Implementor implementor) {
        this.implementor = implementor;
    }

    public abstract void operation();
}

// 扩展抽象类
class RefinedAbstraction extends Abstraction {
    public RefinedAbstraction(Implementor implementor) {
        super(implementor);
    }

    @Override
    public void operation() {
        // 扩展抽象的操作
        implementor.operationImpl();
    }
}

// 示例代码
public class BridgePatternExample {
    public static void main(String[] args) {
        Implementor implementorA = new ConcreteImplementorA();
        Abstraction abstractionA = new RefinedAbstraction(implementorA);
        abstractionA.operation();

        Implementor implementorB = new ConcreteImplementorB();
        Abstraction abstractionB = new RefinedAbstraction(implementorB);
        abstractionB.operation();
    }
}

    In the above example, Implementor defines the implementation interface, and ConcreteImplementorA and ConcreteImplementorB are concrete implementation classes. Abstraction is an abstract class that contains a reference to Implementor and defines the abstract operation interface. RefinedAbstraction is an extension of Abstraction, implements the abstract operation interface, and calls the implementation methods in its operations.

    Through the Bridge Pattern, the specific implementation can be dynamically selected at runtime, and the abstraction and implementation parts can be extended and changed independently. This decoupling helps improve the flexibility and maintainability of the system.
