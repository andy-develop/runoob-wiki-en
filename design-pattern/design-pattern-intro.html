Introduction to Design Patterns

Design patterns represent the best practices, usually adopted by experienced object-oriented software developers. Design patterns are solutions to general problems that software developers face during the software development process. These solutions have been summarized by many software developers through trial and error over a considerable period of time.

Design patterns are a set of repeatedly used, widely known, categorized and cataloged summaries of code design experience. The purpose of using design patterns is to reuse code, make code easier for others to understand, and ensure code reliability. There is no doubt that design patterns are a win-win for oneself, others, and the system. Design patterns make code compilation truly engineering-based, and design patterns are the cornerstone of software engineering, just like bricks and stones of a building. The reasonable use of design patterns in projects can perfectly solve many problems. Each pattern has a corresponding principle in reality. Each pattern describes a problem that repeatedly occurs around us, as well as the core solution to the problem. This is also the reason why design patterns can be widely applied.

What is GOF (full name: Gang of Four)?

在 1994 年，由 Erich Gamma、Richard Helm、Ralph Johnson 和 John Vlissides 四人合著出版了一本名为Design Patterns - Elements of Reusable Object-Oriented Software（中文译名：设计模式 - 可复用的面向对象软件元素）the book, which was the first to mention the concept of design patterns in software development.

Gang of FourGOF（全拼 Gang of Four）The design patterns they proposed are mainly based on the following object-oriented design principles.

  • Program to an interface, not to an implementation.
  • Favor object composition over inheritance.

Use of Design Patterns

Two main uses of design patterns in software development.

A common platform for developers

Design patterns provide a standard terminology system, specific to particular scenarios. For example, the Singleton design pattern means using a single object, so that all developers familiar with the Singleton design pattern can use a single object, and in this way can tell others that the program uses the Singleton pattern.

最佳的实践

Design patterns have undergone a long period of development, and they provide the best solutions to general problems faced in the software development process. Learning these patterns helps less experienced developers learn software design in a simple and quick way.

Advantages of Design Patterns

  • Provides a shared design vocabulary and concepts, enabling developers to better communicate and understand each other's design intentions.
  • Provides proven solutions that can improve software maintainability, reusability, and flexibility.
  • Promotes code reuse, avoiding duplicate design and implementation.
  • By following design patterns, errors and problems in the system can be reduced, and code quality can be improved.

The Six Principles of Design Patterns

1、开闭原则（Open Close Principle）

The Open-Closed Principle means:Open for extension, closed for modificationWhen the program needs to be extended, the original code must not be modified, achieving a hot-swappable effect. In short, it is to make the program highly extensible and easy to maintain and upgrade. To achieve this effect, we need to use interfaces and abstract classes, which we will mention in the later specific design.

2、里氏代换原则（Liskov Substitution Principle）

The Liskov Substitution Principle is one of the basic principles of object-oriented design. The Liskov Substitution Principle states that wherever a base class can appear, a subclass must be able to appear as well. LSP is the cornerstone of inheritance and reuse. Only when a derived class can replace the base class without affecting the functionality of the software unit can the base class truly be reused, and the derived class can also add new behaviors on the basis of the base class. The Liskov Substitution Principle is a supplement to the Open-Closed Principle. The key step in implementing the Open-Closed Principle is abstraction, and the inheritance relationship between base classes and subclasses is the concrete implementation of abstraction. Therefore, the Liskov Substitution Principle is a specification of the concrete steps for implementing abstraction.

3、依赖倒转原则（Dependence Inversion Principle）

This principle is the foundation of the Open-Closed Principle. Specific content: program for interfaces, depend on abstraction rather than on concrete implementations.

4、接口隔离原则（Interface Segregation Principle）

The meaning of this principle is: using multiple isolated interfaces is better than using a single interface. It also has another meaning: reduce the coupling between classes. From this, it can be seen that design patterns are actually software design ideas derived from large-scale software architecture, convenient for upgrading and maintenance, emphasizing the reduction of dependencies and coupling.

5. Demeter's Law, also known as the Least Knowledge Principle (Demeter Principle)

The Least Knowledge Principle means: an entity should interact with other entities as little as possible, so that system functional modules are relatively independent.

6、合成复用原则（Composite Reuse Principle）

The Composite Reuse Principle means: try to use composition/aggregation instead of inheritance.

    Interface Segregation Principle (ISP)

    When designing an application, if a module contains multiple sub-modules, we should be careful about how we abstract the module. Suppose the module is implemented by a class; we can abstract the system into an interface. But when adding a new module to extend the program, if the module to be added only contains some of the sub-modules of the original system, then the system forces us to implement all the methods in the interface, and we would also have to write some dummy methods. Such an interface is called a fat interface or a polluted interface. Using such an interface will introduce some inappropriate behaviors into the system; these inappropriate behaviors may lead to incorrect results, and may also cause a waste of resources.

    1. Interface Segregation

    The Interface Segregation Principle (ISP) states that clients should not be forced to implement interfaces they will not use. Methods in a fat interface should be grouped, and then multiple interfaces should be used to replace it, with each interface serving a submodule. In simple terms, using multiple specialized interfaces is much better than using a single interface.

    The main points of ISP are as follows:

    1) A class's dependency on another class should be based on the smallest interface.

    ISP can achieve not forcing clients (the users of interfaces) to depend on methods they do not use. Implementation classes of interfaces should only present a single-responsibility role (following the SRP principle). ISP can also reduce mutual influence among clients—when a client requests a new responsibility (requires change) and forces the interface to change, the possibility of affecting other client programs is minimized.

    2) Client programs should not depend on interface methods (functions) they do not need.

    Client programs should not depend on interface methods (functions) they do not need—then what should they depend on? They should depend on the interfaces they need. Whatever interface the client needs, provide that interface, and remove the interfaces it does not need. This requires refining the interface to ensure its purity.

    For example, in inheritance, since a subclass inherits all available methods from the parent class, some methods in the parent class may not be needed in the subclass. For instance, both ordinary employees and managers inherit from the Employee interface; employees need to write a daily work log, but managers do not. Therefore, the work log requirement cannot be used to constrain managers, meaning managers should not depend on the method of submitting a work log.

    It can be seen that ISP and SRP overlap to some extent conceptually. In fact, many design patterns overlap conceptually, and it is even hard to tell which design pattern a piece of code belongs to.

    ISP emphasizes that an interface should make as few promises to clients as possible and should be specialized. When the requirements of a client program change and force the interface to change, the chance of affecting other client programs is small. This is essentially the problem of interface pollution.

    2. Interface pollution

    Overly bloated interface design is pollution of the interface. So-called interface pollution means adding unnecessary responsibilities to an interface. If a developer adds a new feature to an interface merely to reduce the number of interface implementation classes, this design will cause the interface to be continually "polluted" and "fattened".

    "Interface Segregation" is actually the principle of customized service design. Use multiple inheritance of interfaces to combine different interfaces, thereby externally providing combined functionality—achieving "service on demand". An interface should be split, but not too finely; there must be a standard, which is high cohesion. An interface should have some basic functions and be able to independently complete a basic task.

    In practical applications, you may encounter the following problem: for example, if I need a DAO implementation that can adapt to multiple types of databases, I should first implement a database operation interface that specifies some basic methods for database operations, such as connecting to the database, adding, deleting, modifying, querying, and closing the database. This is a minimal-functionality interface. For some MySQL-specific methods that do not exist in other databases or have different natures, such as MySQL's pconnect method possibly used in PHP, no equivalent concept exists in other databases, so this method should not appear in this basic interface. Then what basic methods should this basic interface have? PDO has already told you.

    PDO is an abstract database interface layer; it tells us what basic methods a basic database operation interface should implement. An interface is a high-level abstraction, so the methods in an interface should be universal, basic, and not prone to change.

    There is another question: how should those specific methods be implemented? According to the ISP principle, these methods can exist in another interface, and let this "odd one" implement both interfaces simultaneously.

    For interface pollution, two handling approaches can be considered:

    • Separate interfaces using delegation.
    • Separate interfaces using multiple inheritance.

    In the delegation pattern, two objects participate in handling the same request; the object that receives the request delegates it to another object for processing. For example, the strategy pattern and proxy pattern both apply the concept of delegation.

    Design pattern type examples

    1. Creational Patterns

    FACTORY? A processing factory: give it "M4A1", it produces a police gun for you; give it "AK47", you get a criminal's gun. The gun-purchasing program in CS must use this pattern.

    BUILDER? A production assembly line: in the past, parts were produced one by one manually in handicraft workshops and then assembled step by step. It is like after the Industrial Revolution, everything is now replaced by production assembly lines. To build a Toyota car, first define the car's structure, such as consisting of tires, steering wheel, and engine. Then produce Toyota's tires, steering wheel, and engine according to this structural standard. Then assemble them. Finally, you get a Toyota car.

    PROTOTYPE? The invention of printing: before, one could only copy by tracing or transcribing, which was time-consuming, laborious, and extremely inefficient. With printing, it is fast.

    SINGLETON? Ensuring uniqueness: it's not achieved by "new", but by "instance", and it must be instantiated so that there is only one instance in the whole world (this poor class — does it even deserve to be called a "class"?). Look at the Singleton class code.

    2. Structural Patterns

    ADAPTER? An interpreter: Brother Hu only knows Chinese, Bush only knows American English, and the interpreter is fluent in both Chinese and American—that's an Adapter.

    DECORATOR? Decoration: a name can identify a person. To show respect for a person, one generally addresses them as "Honorable". With decoration, it looks much better.

    BRIDGE? A white horse is not a horse: horses can be black or white in color, and male or female in gender. Saying "this is a horse" is too abstract; saying "this is a black male horse" is too rigid. Only by dynamically combining color and gender with the horse does "this is a (black or white) (male or female) horse" become flexible and elegant. That captures the essence of the Bridge pattern.

    COMPOSITE? A big family: sons give birth to grandsons, grandsons give birth to sons, and so on endlessly. Organizing many varied people into a large family arranged by seniority is the implementation of this pattern.

    FACADE? Seeking common ground while reserving differences: to graduate from high school, one must attend middle school and high school; a PhD also must attend middle school and high school. Therefore, the state has universalized middle school and high school into nine-year compulsory education.

    FLYWEIGHT? Once and for all: knowing three thousand Chinese characters enables one to handle daily reading and writing. This shows the importance of having this Chinese character library in the mind.

    PROXY? Ruling behind the curtain: like the four chief ministers during the Kangxi reign of the Qing Dynasty, much power was not in the emperor's hands, and matters had to be handled through assisting ministers.

    3. Behavioral Patterns

    CHAIN OF RESPONSIBILITY? Renting a house: before, one had to ask around everywhere to find a house, which was inefficient and failed to find good listings. Now with housing agencies, you make a rental request to the agency; the agency provides a suitable property. If satisfied, you stop requesting; if not, you continue viewing until satisfied.

    COMMAND? Killing with a borrowed knife: previously, one killed whoever one wanted, but after a while realized that continuing so would create too many enemies. So one acted through others, stirring up relationships among others to achieve one's own goals.

    INTERPRETER? Classical Chinese annotation: take a passage of classical Chinese and translate it into vernacular Chinese.

    ITERATOR? Wipe them all out: search one by one, never letting a single one escape;

    MEDIATOR? Triangular debt: originally a tangled web of debt relationships; suddenly an intermediary appears and takes over everything, so the triangular relationship becomes three independent parties seeking a fourth-party intermediary.

    MEMENTO? Sharing blessings: however much I have, you have that much.

    OBSERVER? A watchman: once the watched person has any abnormal situation, he will definitely respond in time.

    STATE? Freedom to enter and exit: like a door that can be entered and exited. If many people come and go at any time, it will appear chaotic and unsafe. Now a security guard is set to restrict entry and exit, so each person's entry and exit appears orderly.

    STRATEGY? Long illness makes the patient a doctor: a person's illness may have various symptoms, but after long-term exploration, one can summarize several types such as colds, lung disease, and hepatitis.

    TEMPLATE METHOD? Theory doesn't necessarily have to be practiced: it is enough that the coach's students can swim; whether the coach himself can swim or not is irrelevant.

    VISITOR? Punish according to law: because Zhang San killed someone and must be executed, Li Si stole and must be fined. This necessitates establishing a penalty system, so laws are enacted specifying what punishments crimes such as murder, arson, and theft should receive, and after passage, changes should be minimal. In the future, whoever commits a crime, the punishment is based on the common regulations—this is the whole process of the birth of the Visitor pattern.
