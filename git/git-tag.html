Git 标签

If you reach an important stage and want to always remember the snapshot of a commit, you can usegit tagTag it.

Git tags are used to mark specific commit points in a repository, typically for release versions (such as v1.0, v2.0).

For example, if we want to release a "1.0" version for our runoob project, we can usegit tag -a v1.0The command tags the latest commit (HEAD) with "v1.0".

-a选项意为

"创建一个带注解的标签"，不用-a选项也可以执行的，但它不会记录这标签是啥时候打的，谁打的，也不会让你添加个标签的注解，我们推荐一直创建带注解的标签。

Tag syntax format:

git tag <tagname>

例如：

git tag v1.0

-aThe option can add an annotation:

$ git tag -a v1.0

When you run the git tag -a command, Git will open your editor and let you write a tag annotation, just like writing an annotation for a commit.

Now, note that when we executegit log --decorateAt this point, we can see our tag:

*   d5e9fc2 (HEAD -> master) Merge branch 'change_site'
|\

|/  
* c1501a2 removed test.txt、add runoob.php

If we forgot to tag a commit and already released it, we can add a tag to it afterwards.

For example, suppose we released commit 85fc7e7 (the last line in the example above), but forgot to tag it at that time. We can now also:

$ git tag -a v0.9 85fc7e7
$ git log --oneline --decorate --graph

|/

* 3b58100 (tag: v0.9) 第一次版本提交

If we want to view all tags, we can use the following command:

$ git tag
v0.9
v1.0

Push tags to the remote repository

By default, git push does not push tags; you need to explicitly push tags.

git push origin <tagname>

Push all tags:

git push origin --tags

Delete lightweight tag

本地删除：

git tag -d <tagname>

远程删除：

git push origin --delete <tagname>

附注标签

Annotated tags store the creator's name, email, date, and can contain tag information. Annotated tags are more formal and suitable for scenarios that require additional metadata.

Syntax for creating annotated tags:

git tag -a <tagname> -m "message"
例如：
git tag -a <tagname> -m "runoob.com标签"

PGP-signed tag command:

git tag -s <tagname> -m "runoob.com标签"

View tag information:

git show <tagname>

实例

The following is a comprehensive example demonstrating how to create, view, push, and delete tags.

Creating lightweight tags and annotated tags:

git tag v1.0
git tag -a v1.1 -m "runoob.com标签"

Viewing tags and tag information:

git tag
git show v1.1

Push tags to the remote repository:

git push origin v1.0
git push origin v1.1
git push origin --tags  # 推送所有标签

删除标签

本地删除：

git tag -d v1.0

远程删除：

git push origin --delete v1.0

    1. Tag introduction

    When releasing a version, we usually create a tag in the repository first, which uniquely identifies the version at the moment of tagging. In the future, no matter when you retrieve the version of a certain tag, you are extracting the historical version from the moment that tag was created.

    Therefore, a tag is also a snapshot of the repository.

    Although a Git tag is a snapshot of the repository, it is actually just a pointer to a specific commit (similar to a branch, right? But branches can move, while tags cannot), so creating and deleting tags are both done instantly.

    Git has commits, so why introduce tags?

    "Please package and release the version from last Monday, the commit number is 6a5819e…"

    "A bunch of messy numbers is hard to find!"

    If we use another approach:

    "Please package and release the version from last Monday, the version number is v1.2"

    "OK, just look up the commit according to tag v1.2!"

    So, a tag is an easy-to-remember, meaningful name that is bound to a specific commit.

    Like most VCSs, Git can also tag versions at a certain point in time. People often do this when releasing a software version (such as v1.0, etc.).

    In this section, we will learn how to list all available tags, how to create new tags, and the differences between different types of tags.

    新建标签

    Git uses two types of tags:Lightweight和Annotated。

    A lightweight tag is like a branch that does not change; in fact, it is just a reference pointing to a specific commit object.

    An annotated tag, on the other hand, is actually an independent object stored in the repository. It has its own checksum information, containing the tag name, email address, and date, as well as a tag message. The tag itself can also be signed or verified using GNU Privacy Guard (GPG).

    In general, we recommend using annotated tags to preserve relevant information;

    Of course, if you are just temporarily adding a tag, or don't need additional annotation information, using a lightweight tag is also fine.
