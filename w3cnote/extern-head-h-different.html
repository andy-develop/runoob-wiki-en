The difference and connection between extern and header files (*.h)

Category

用 #includeWhy do we still need the extern keyword when we can include declarations of variables and functions from other header files?

If I want to reference a global variable or function a, can't I just directly include #include<xxx.h> in the source file (xxx.h contains the declaration of a)? Why do I still need to use extern?

This question, which seemed right but was actually wrong, troubled me for a long time. After practice and consulting materials, I have the following summary:

I. Header files

First, let's talk about header files. Actually, header files have no real effect on the computer. They are only expanded at the location during precompilation...#include...it is expanded, and there is no other meaning. Actually, header files are mainly for others to read.

I did an experiment. I changed the extension of the header file to xxx.txt, and then used #include "xxx.txt" where the header file was referenced. Compilation and linking both passed smoothly. From this, it can be seen that header files only serve the purpose of reading code; they have no other function!

Whether it's C or C++, you put your functions, variables, or structs, classes, etc. into your .c or .cpp files. Then compile them into lib, dll, obj, .o, etc. Then when others use them, the most basic [command] is gcc hisfile.cpp yourfile.o|obj|dll|lib, etc.

But for us programmers, how do they know what exactly is in your lib, dll...? They need to look at your header file. Your header file is the documentation for users: explanations of functions, parameters, and various interfaces.

Since it is documentation, what naturally goes in the header file are the 'declarations' of functions, variables, and classes (for functions, also called function prototypes). Remember, it's 'declaration', not 'definition'.

Now, I assume everyone knows the difference between declaration and definition. Therefore, it's best not to foolishly define anything in a header file. For example, a global variable:

/*xx头文件*/
#ifndef _XX_头文件.H
#define _XX_头文件.H
int A;
#endif

Then, unfortunately, the int A here is a definition of a global variable, so if this header file is referenced multiple times, your A will be defined repeatedly, which is obviously syntactically wrong. However, with the conditional compilation of #ifndef, it can ensure that your header file is only referenced once, so maybe there won't be any trouble, but if multiple c files include this header file, errors will still occur, because the effective scope of the macro name is limited to the current c source file. Therefore, no error will occur during compilation of these multiple c files, but an error will be reported during linking, saying that you have defined the same variable in multiple places:

Linking...
incl2.obj : error LNK2005: "int glb" (?glb@@3HA) already defined in incl1.obj
Debug/incl.exe : fatal error LNK1169: one or more multiply defined symbols found

II. extern

This keyword is really quite annoying. When defining a variable, this extern can actually be omitted (all are omitted by default when defining). When declaring a variable, this extern must be added before the variable, so sometimes it makes you confused about whether it is a declaration or a definition. In other words, having extern before a variable is not necessarily a declaration, but having no extern before a variable can only be a definition. Note: a definition allocates memory space for the variable, while a declaration does not need to allocate memory space for the variable.

Below, I'll discuss it in two categories: variables and functions.

(1) Variables

Especially for variables:

extern int a; // 声明一个全局变量 a
int a; // 定义一个全局变量 a
extern int a =0 ; // 定义一个全局变量 a 并给初值。
int a =0;    // 定义一个全局变量 a, 并给初值，

The fourth one is the same as the third one; both define a global variable that can be used externally and provide an initial value.

Confused, right? They really look alike. But a definition can only appear in one place. That is to say, whether it's int a; or extern int a=0; or int a=0;, they can only appear once, while that extern int a can appear many times.

When you want to reference a global variable, you must declare it, extern int a; At this time, extern cannot be omitted, because if omitted, it becomes int a;, which is a definition, not a declaration. Note: in extern int a;, the type int can be omitted, i.e., extern a; but other types cannot be omitted.

(2) Functions

For functions, it's the same. There are also definitions and declarations. When defining, use extern to indicate that this function can be referenced externally; when declaring, use extern to indicate that this is a declaration. But because function definitions and declarations are different—a function definition requires a function body, while a function declaration has no function body (and ends with a semicolon)—extern can be omitted in both function definition and declaration. After all, other files also know that this function is defined elsewhere, so it's fine without extern. The two are so different that omitting extern won't cause any problems.

For example:

/*某cpp文件*/
int fun(void)
{
      return 0;
}

Good, we have defined a global function:

/*另一cpp文件*/
int fun(void);

We made a declaration of it, and then we can use it afterwards. Whether to add extern or not is the same. We can also put the declaration of fun in a header file, and finally it becomes like this:

/*fun.h*/
int fun(void);   //函数声明，所以省略了extern，完整些是extern int fun(void);
/*对应的fun.cpp文件*/
int fun(void)
{
     return 0;
}//一个完整的全局函数定义，因为有函数体，extern同样被省略了。

Then, a customer—a customer who wants to use your fun—includes this header file, and okay, it's a global declaration. No problem.

But correspondingly, if this customer wants to use a global variable, then they need extern some variable; otherwise it becomes a definition.

Summary:

For variables: if you want to use a variable from another source file (e.g., file B) in the current source file (e.g., file A), there are two methods: (1) in file A, you must use extern to declare the variable defined in file B (of course, a global variable); (2) in file A, add the header file corresponding to file B. Of course, this header file contains the variable declaration in file B, that is, in this header file you must use extern to declare the variable; otherwise, the variable will be defined once more.

For functions: if you want to use a function from another source file (e.g., file B) in the current source file (e.g., file A), there are two methods: (1) in file A, use extern to declare the function defined in file B (actually, extern can also be omitted; it is only necessary for the function prototype of the function defined in file B to appear in file A); (2) in file A, add the header file corresponding to file B. Of course, this header file contains the function prototype in file B. In the header file, functions don't need extern.

Another way to state the above summary:

(a) For calling a global variable from another file in one file: because global variables are generally defined in the original .c file, we cannot use #include to include source files; we can only include header files. So the common method is to use extern int a to declare an external variable. Another method is: after defining a global variable int global_num in the a.c file, you can write extern int global_num in the corresponding a.h header file, so that other source files can declare it as an external variable by including a.h.

(b) There are also different examples of variables and functions.int fun(); 和 extern int fun();They are all declarations (definitions require an implementation body). Using...extern int fun()...is just to more clearly indicate that it is a declaration. While...int a;...is a definition.extern int a;...is a declaration.

(3) In addition, the extern modifier can be used for the specification issue of calling C functions in C++ programs.

For example, to call C library functions in C++, you need to use extern "C" in the C++ program to declare the functions to be referenced. This is used by the linker, telling the linker to link according to the C function specification when linking. The main reason is that C++ and C programs have different naming rules in the object code after compilation.

When compiling, in order to solve the polymorphism problem, the C++ language combines the name and parameters to generate an intermediate name, while the C language does not. Therefore, it can cause the situation where the corresponding thing cannot be found during linking. At this time, C needs to use extern "C" to specify the linking, which tells the compiler: please keep my name and do not generate an intermediate name for linking for me.

III. The connection between extern and header files

This connection also solves the two questions raised at the beginning:

(a) Since #include can include declarations of variables and functions from other header files, why still use the extern keyword?

(b) If I want to reference a global variable or function a, I just directly include #include in the source file......(xxx.h contains the declaration of a) and that's enough? Why still use extern?

Answer: If one file (say file A) needs to reference a large number of variables or functions defined in another file (say file B), then using a header file is more efficient and the program structure is more standardized. Other files (e.g., files C, D, etc.) that want to reference variables or functions defined in file B only need to use #include to include the header file corresponding to file B (of course, this header file only contains declarations of variables or functions, and must never contain definitions).

That was a forgotten era—an era when compilers only knew .c (or .cpp) files and did not know what .h was.

At that time, people wrote many .c (or .cpp) files. Gradually, people found that the variable declarations or function prototypes in many .c (or .cpp) files were the same, but they had to type these contents into every .c (or .cpp) file word by word, repeatedly. But even more terrifying was that when one of the declarations changed, they needed to check all the .c (or .cpp) files and modify the declarations in them. Ah~, it was simply doomsday!

Finally, someone (or maybe some people) could no longer endure such torment. He (they) extracted the repeated parts, put them in a new file, and then typed statements like #include XXXX in the needed .c (or .cpp) files. In this way, even if a declaration changed, there was no longer any need to search everywhere and modify—the world was still so beautiful!

Because this new file was often placed at the head of .c (or .cpp) files, it was named 'header file', with the extension .h.

From then on, the compiler (actually, its preprocessor) knew that besides .c (or .cpp) files, there was also a .h file, as well as a command called #include.
